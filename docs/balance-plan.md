# ゲームバランス自動調整 計画

対象: `や球`（`app.js` / `styles.css` / `trivia.js`）
目的: 「**巧拙が勝敗に直結する**」を保ちながら、数値バランスの調整を**人の勘ではなく機械で回せる**ようにする。

---

## 0. 結論（先に）

1. **実行中に難度を変える自動調整（DDA・ハンディ）はやらない。**
   2人が同じ端末で向かい合い、半イニングごとに攻守を交代する**対称ゲーム**なので、片方を勝たせるために内部の数値を動かすと「操作で差がついた」という体験そのものが壊れる。READMEの方針1に真正面から反する。
2. **やるのは「オフラインの自動チューニングループ」。**
   本物の `app.js` を Playwright + Chromium で高速再生し、腕前の違うボット同士に何百試合もさせ、**試合の形**（得点分布・接戦率・腕前差の勝率）を測り、`physics` の引き手を機械的に動かして目標に近づける。最終的な採用判断は人が実機で遊んで行う。
3. **「バランスが取れている」の定義を先に数値で決める。**
   これが無いと何回回しても終わらない。本書 §3 に初期値を置くので、まずそこを合意してから着手する。

## 1. 現状の把握（調査結果）

### 1.1 ゲームの構造

- 単一の `<script>`（モジュールでない）。`physics`・`playingState`・`gameState` と全関数がグローバル。**`page.evaluate` から直接叩ける**（READMEの計測手順もこの前提）。
- メインループは `animatePlaying(timeStamp)` で、`dt = min((now - lastTick)/1000, 0.032)`。**rAF のタイムスタンプ駆動**。
- 入力は Pointer Events（`beginPlayingPointer` / `move` / `end`）。上半分=投手/守備、下半分=打者。守備モード中は下 1/4 が連打エリア（`runnerBoostAreaTopRatio: 0.75`）。マルチタッチ前提。
- 乱数は `Math.random()` が **打撃の角度ばらつき**（`battingSwingAngleVariation`）、デモ投球、演出、ID生成に使われている。対戦中の勝敗に効く乱数は実質スイング角のばらつき 0.05rad だけ。**ほぼ決定論的な物理ゲーム**。
- UI の待ち（`CHANGE!` 2700ms、デッドボール 3600ms、投球クールダウン 900ms など）は `setTimeout` と rAF の両方で動いている。高速化にはタイマーの仮想化が要る。
- 保存は IndexedDB（250ms デバウンス）。試合途中の再開に使っている。

### 1.2 すでにある「引き手」（README「現在の主要パラメータ」より）

| 領域 | パラメータ | 性質 |
| --- | --- | --- |
| 走者 | `runnerBaseSpeed` 13 / `runnerBoostPerTap` 43 / `runnerBoostMax` 154 | **3つ同倍率**で全体速度。`Max` 単独で上限だけ |
| 走者 | `runnerBoostDecayRate` 2.6 | 時定数。**触ると手応えが変わる**ので最後に |
| 守備 | `PLAYING_RUNNER_HIT_RADIUS` 17（定数） | `.runner-target-ring` 31px と**比率固定** |
| 守備 | `fielderThrowSpeedFactor` 0.6 / `deepHitPickupDelay` 0.7 | 守備の強さ |
| 打撃 | `batContactRadius` 35 / `battingSwingLingerDuration` 0.085 / `battingSwingThreshold` 330 | 当てやすさ |
| 長打 | `homeRunClearRatio` 0.18 / `homeRunHitQuality` 0.8 | HR 率。**盤面比を維持** |
| 投球 | `deadBallRadius` 20.8 / `pitchReleaseGrace*` | デッドボール・投げやすさ |

### 1.3 現在の力関係（READMEの実測）

打球6パターン × 一塁到達競争で、**秒6回連打→6中6 守備勝ち、秒12回→6中5 守備勝ち**。走者側にやや厳しい。
→ これは「1本の打球を1人の走者が走る」ミクロ計測。**試合全体の形（得点・接戦率）はまだ測られていない。** 本計画はここを埋める。

### 1.4 制約（READMEの「やらない方がいいこと」を引き継ぐ）

- 打球を拾いにくくする方向での調整はしない
- HR 条件を絶対 px に戻さない
- 画面に情報を足さない
- 数値は**実測で決める**。感覚値を入れない

## 2. なぜ「実行中の自動調整」ではなく「オフライン」か

| 観点 | 実行中 DDA（ハンディ） | オフライン自動チューニング（本計画） |
| --- | --- | --- |
| 方針1「巧拙が直結」 | ✗ 下手な側を勝たせると矛盾 | ○ 数値は全員同じ。差は腕前だけ |
| 対称2人対戦との相性 | ✗ 半イニングで攻守が入れ替わるので「誰を助けるか」が定まらない | ○ 「役割間の釣り合い」と「腕前差の反映度」を直接測れる |
| 1台マルチタッチ・リアルタイム | ✗ 1人分の操作を切り出して評価する手段がない（2本の指が同時） | ○ ボットで役割ごとの腕前を独立に振れる |
| 透明性 | ✗ 裏で動く。「今なぜ届かなかった？」が説明できない | ○ 全部 `physics` の固定値。README に実測で残せる |
| 発展の余地（方針4） | 個別数値を隠れて動かす | 「仕組み」の変更を同じ土俵で評価できる |

実行中に動かすものがあるとすれば、**明示的に選ぶハンディ（親子で遊ぶ用など）**だけ。これは「自動調整」ではなく「設定」で、本計画の範囲外（§8 に将来案として記す）。

## 3. 「バランスが取れている」の定義（目標指標）

**ここが合意事項。** 数値は初期案で、Phase 1 のベースライン計測後に見直す。

### 3.1 試合の形（同腕前同士、3回制 / 9回制それぞれ）

| 指標 | 目標 | 理由 |
| --- | --- | --- |
| 1試合の合計得点（中央値） | 3回制: 3〜6点 / 9回制: 6〜14点 | 0-0 続きも乱打戦も退屈。実際の野球より少し多め |
| 両軍無得点の試合 | 10% 未満 | 「何も起きなかった」をなくす |
| 接戦率（1点差以内 or 同点で終わる） | 35〜50% | 対称対戦の核。50% を超えると運ゲーに見える |
| 1打席あたりの結果分布 | 三振 20〜30% / 四球 5〜15% / インプレー 55〜70% | 投手が「ゾーンに投げる価値」と打者が「振る価値」の両立 |
| インプレー時のアウト率 | 55〜70% | README 実測は 83〜100%。走者側に少し戻す |
| HR 率（インプレー比） | 3〜8% | 「芯の一撃」の希少性を保つ |
| デッドボール率（投球比） | 2% 未満 | 得点源として狙えないこと |
| 試合時間（3回制, 実時間換算） | 6〜10分 | 1台を囲んで遊ぶ長さ |
| 無操作時間の比率 | 20% 未満 | テンポ |

### 3.2 腕前差の反映度（最重要・方針1）

| 対戦カード | 目標勝率（上手い側） |
| --- | --- |
| 上級 vs 初級 | **85% 以上** |
| 上級 vs 中級 | 65〜75% |
| 中級 vs 初級 | 65〜75% |
| 同腕前 | 50% ± 5%（200試合） |

さらに**単調性**: 各入力精度（連打間隔・送球の先読み誤差・スイングのタイミング誤差）を単独で良くしたとき、結果指標（出塁率・アウト率・打率）が**単調に**改善すること。途中で頭打ちや逆転があれば「報われない操作」なので、§1.2 の該当パラメータが要調整。

### 3.3 役割の対称性

- 同腕前同士で**表（青攻撃）と裏（赤攻撃）の得点が等しい**こと（差 5% 以内）。
  表裏で仕様差はないはずだが、画面の上下反転や「最終回裏サヨナラ」で偏る可能性を監視する。

### 3.4 退化戦略の不在

次の「一つの操作だけで勝てる」戦略が、同腕前の総合ボットに勝率 60% を超えないこと。

- 走者: 連打せず止まりっぱなし / 常に最速連打（止まらない）
- 守備: 拾ってすぐ投げる（先読みなし） / 走者が止まるまで投げない
- 投手: 全球ゾーン外（四球狙いと見せかけた見逃し誘い） / 全球デッドボール狙い
- 打者: 全球見逃し / 全球フルスイング

### 3.5 ガードレール（下げてはいけないもの）

- フレーム時間 p95 < 20ms（守備中・走者3人・連打あり、README の計測条件）
- README 記載の既存実測値（本塁→一塁 秒3回 6.7s / 秒6回 3.9s / 秒12回 2.8s、避け性能 0.4s で 23px など）が、**同じ数値のままなら再現すること**（ハーネスの健全性テスト）

## 4. 全体アーキテクチャ

```
┌──────────────────────────────────────────────────────────────┐
│ tools/balance/                                                │
│                                                              │
│  harness/      Playwright で index.html を開き、               │
│                仮想時計で高速再生する土台                        │
│  bots/         投手・打者・走者・守備の腕前モデル                 │
│  metrics/      1球・1打席・1試合 → §3 の指標に集計              │
│  tune/         パラメータを動かして試合を回し、目標との距離を最小化 │
│  report/       before/after を Markdown + 図で出力             │
└───────────────┬──────────────────────────────────────────────┘
                │ page.evaluate / CDP Input.dispatchTouchEvent
                ▼
        index.html + app.js（本番コードそのまま）
        + window.__yakyuTest（テスト用の最小フック）
```

**原則: ゲームの物理を別実装（シミュレータ）に写し取らない。** 写すとそのうちズレて、ズレた方を調整することになる。計測は必ず本物の `app.js` で行う。

### 4.1 `app.js` 側に足す最小フック

本番の挙動を変えない範囲で、以下だけ足す（`?test=1` クエリか `window.__YAKYU_TEST__` フラグで有効化）。

```js
// app.js 末尾付近
if (new URLSearchParams(location.search).has("test")) {
  window.__yakyuTest = {
    physics, playingState, gameState,
    // 乱数の差し替え（シード付きで再現可能に）
    setRandom(fn) { randomSource = fn; },
    // 1球・1打席・アウト・得点・チェンジのイベントログ
    events: [],
    // 盤面の実寸（塁・本塁・マウンド・ゾーン）
    geometry() { ... },
  };
}
```

- `Math.random()` の直接呼び出しを `randomSource()` に寄せる（既定は `Math.random`）。
- `gameProcessStrike/Ball/Out/Score`、`spawnRunnerOnHit`、`applyRunnerTagOut`、`launchPlayingBall` の入口で `events.push({t, type, ...})`。
- **時間の仮想化は app.js 側では触らない**。Playwright の `page.clock`（`install` + `runFor`）で `requestAnimationFrame` / `setTimeout` / `performance.now` / `Date.now` をまとめて進める。`dt` は 0.032 でキャップされているので、仮想時計を 16.67ms 刻みで進めれば実機 60fps と同じ積分になる。

### 4.2 入力の与え方（2段構え）

| 層 | 方法 | 用途 |
| --- | --- | --- |
| **A. 内部関数直叩き** | `spawnRunnerOnHit()`、`launchPlayingBall(vector)`、`applyRunnerBoostTap()` など | ミクロ計測（速度曲線・当たり判定の実寸・6パターン競争）。速い。README の既存計測をそのまま移植 |
| **B. ポインタイベント合成** | CDP `Input.dispatchTouchEvent` で**2本指同時**のスワイプ・タップ | フル試合。投球の `pitchReleaseGrace`、スイング速度判定（`battingSwingThreshold`）、連打エリア判定など**入力経路のパラメータ**まで含めて評価 |

B を正とし、A は B の高速な近似・単体テストとして使う。A と B の結果がズレたら入力経路に見落としがあるサイン。

### 4.3 高速化の見込み

- 仮想時計で 1 フレーム = `page.clock.runFor(16.67)`。描画は headless でも走るので、**1試合（3回制）を実時間 10〜20 秒**程度を見込む。
- Playwright のブラウザコンテキストを 8〜16 並列にすれば **1時間で 2,000〜4,000 試合**。チューニングの1反復（1パラメータ組 × 6カード × 100試合 = 600試合）が 10〜20 分。
- UI の待ち時間（`CHANGE!` など）はボットが「次の操作」を待つだけなので、仮想時計を飛ばして詰められる（§3.1 の試合時間は仮想時計で測るので影響なし）。

## 5. ボット（腕前モデル）

4つの役割を**独立したパラメータ**で表す。腕前は「操作の誤差」と「判断の質」の2軸。実測値のある項目は README の数値から初期化する。

### 5.1 投手

| パラメータ | 初級 | 中級 | 上級 |
| --- | --- | --- | --- |
| 狙った位置からのばらつき σ（px） | 40 | 22 | 10 |
| 球速の選択幅（`minForward`〜`maxForward` に対する比） | 0.4〜0.7 | 0.5〜0.9 | 0.6〜1.0 |
| 曲げる確率 / 曲げ量 | 0.2 / 小 | 0.5 / 中 | 0.7 / 大 |
| コース配分（ゾーン内:際:外） | 7:2:1 | 5:3:2 | 4:4:2 |
| デッドボール狙い（指の位置を見て投げる） | なし | 5% | 15% |

### 5.2 打者

| パラメータ | 初級 | 中級 | 上級 |
| --- | --- | --- | --- |
| タイミング誤差 σ（ms） | 90 | 50 | 25 |
| バット位置の誤差 σ（px） | 30 | 15 | 7 |
| スイング速度（`battingSwingThreshold` に対する比） | 1.1〜1.6 | 1.3〜2.2 | 1.8〜3.0 |
| 見逃し判断（ボール球を見送れる確率） | 0.3 | 0.6 | 0.85 |
| 指をボールの通り道から外す | しない | 遅れて | 常に |

### 5.3 走者

| パラメータ | 初級 | 中級 | 上級 |
| --- | --- | --- | --- |
| 連打間隔（回/秒） | 3 | 6 | 10〜12 |
| 連打間隔のゆらぎ CV | 0.4 | 0.25 | 0.15 |
| 「止まって避ける」を使うか | なし | 送球を見てから（反応 350ms） | 送球直前を予測（反応 180ms） |
| 止まる長さ（ms） | — | 500 | 250〜350 |

### 5.4 守備

| パラメータ | 初級 | 中級 | 上級 |
| --- | --- | --- | --- |
| 拾える瞬間からの反応遅れ（ms） | 500 | 300 | 180 |
| 先読みモデル | 現在位置を狙う | 等速外挿 | 等速外挿＋連打の鳴りを見て減速補正 |
| 狙いのばらつき σ（px） | 25 | 14 | 7 |
| 外したあとの拾い直し遅れ（ms） | 700 | 400 | 250 |

### 5.5 ボットの妥当性確認（これをやらないと全部砂上）

- README の既存実測（本塁→一塁の秒数、避け性能、6パターン競争の 6/6・5/6）を**ハーネスで再現**できること。
- 初級〜上級の値は仮置き。**Phase 5 の実プレイ記録**で分布を校正する。
- ボットは「上手いAI」ではなく「人の手の癖の近似」。上級でも σ をゼロにしない。

## 6. チューニング手順

### 6.1 動かすパラメータと拘束

| 群 | 動かす | 拘束 |
| --- | --- | --- |
| 走者速度 | `runnerBoostMax`（単独）、または Base/PerTap/Max 同倍率 | `DecayRate` は固定（手応え） |
| 守備 | `PLAYING_RUNNER_HIT_RADIUS`、`fielderThrowSpeedFactor`、`deepHitPickupDelay` | `.runner-target-ring` を同比率で連動（31/17 ≒ 1.82） |
| 打撃 | `batContactRadius`、`battingSwingLingerDuration` | |
| 長打 | `homeRunClearRatio`、`homeRunHitQuality` | 盤面比のまま |
| 投球 | `deadBallRadius` | 輪の見た目と同値 |

全部で 8〜9 次元。一度に全部は回さない。

### 6.2 進め方（段階的に次元を増やす）

1. **感度分析（1次元ずつ）**: 各パラメータを現在値の 0.7 / 0.85 / 1.0 / 1.15 / 1.3 倍にして、§3 の全指標を測る。**どの引き手がどの指標に効くか**の表を作る。README の「引き手の効き」を定量化する作業で、これだけでも価値がある。
2. **主効果で粗調整**: 感度表を見て、目標から最も外れている指標に最も効く 2〜3 本を座標降下で動かす。
3. **多次元の仕上げ**: 残差が小さくなったら、3〜5 次元を Nelder–Mead か小さなベイズ最適化（`scikit-optimize` 相当を Node で、または Python 併用）で詰める。評価関数は

   ```
   loss = Σ_i w_i · max(0, |m_i − target_i| − tol_i)²
        + Σ_j penalty_j（ガードレール違反は大きな定数）
   ```

   `w_i` は §3.2 の腕前反映度を最大、次に接戦率・得点中央値。
4. **候補の提示**: loss 上位 3 組を「変更点 / 指標 before→after / 確信度（試合数と信頼区間）」で Markdown レポートに出す。**人が実機で遊んで採用を決める。** 自動コミットはしない。

### 6.3 ノイズ対策

- 1 組あたり最低 100 試合 × 6 カード。勝率の 95% 信頼区間が ±10% を切る数。
- 共通乱数（CRN）: 同じシード列を全パラメータ組で使い、差分のノイズを減らす。
- 腕前の対戦カードは必ず**両側入れ替え**（青が上級／赤が上級）で表裏の偏りを打ち消す。

## 8. 決めておくこと（確認したい点）
