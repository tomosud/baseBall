# バランス改善ループ 運用計画

前提: `docs/balance-plan.md`（全体方針）、`docs/balance/baseline-notes-20261002.md`（現状の所見）。
本書は「何を・どの順で・誰（人／どの AI）が・いくらで」回すかの運用計画。

---

## 0. 全体の流れ

```
[1] ハーネスを main に入れる
      ↓
[2] 明らかな調整を先にやる（ハーネスで before/after を測って、人が実機で確認して、main へ）
      ↓
[3] テストプレイでデータを取る（AI は見ていない。端末内に記録 → 書き出し → リポジトリへ）
      ↓
[4] 評価（機械的な集計は AI 不要。要約は安い AI。判断は高い AI を短時間）
      ↓
[5] 改善（変更 → ハーネス → 実機確認 → main）  → [3] へ戻る
```

AI が介在するのは **[4] の要約と判断、[5] のコード変更** だけ。[3] のテストプレイ中は AI は一切動かない。

## 1. ハーネスを main に入れる

- `docs/balance-plan` ブランチを PR で main にマージする。
- 変更の中身は3つ: 計画書・所見（docs）、ハーネス（`tools/balance/`）、`app.js` のテストフック。
- `app.js` の変更は `?test=1` のときだけ有効で、本番の挙動は変えていない（`eventTime` は本番では `event.timeStamp` を返す、`setPointerCapture` の try/catch は失敗時も状態が崩れないようにする安全側の変更）。
- マージ後、README の「調整のやり方」に `tools/balance` への参照を1行足す（計測コマンドを誰でも実行できるようにする）。

**判断が要るところ**: PR を立てて確認してからマージするか、直接マージするか。推奨は PR（差分を一度目で見てもらう）。

## 2. 明らかな調整（先にやるもの）

所見のうち、**ボットの腕前設定に依存せず構造的に言えるもの**だけを対象にする。デッドボールは現状維持（決定済み）。

| # | 症状 | 根拠（ボット非依存） | 候補の引き手 | 受け入れ基準（ハーネス） |
| --- | --- | --- | --- | --- |
| A | 打球速度が上限 980 に張り付く | `launchSpeed` はスワイプ 1500px/s 程度で上限に届く。普通のフリックで常に最速 | `batHitPowerScale` 0.55 を下げる、または impulse を tanh で圧縮して「芯で捉えたときだけ上限」にする | 中級同士の打球速度 p10/中央/p90 が 980 一色でなく分布を持つ。インプレー時アウト率が 30〜60% |
| B | HR の門番が芯度だけ | 速度上限の打球は `homeRunClearRatio` 0.18 を常に満たす（残り 890px ≫ 127px） | A を直すと自然に効き始める。足りなければ `homeRunHitQuality` 0.8 → 0.85〜0.9 | HR 率（インプレー比）3〜15% |
| C | 三振が出ない（接触窓 ±80ms） | スイング 0.065 + 猶予 0.085、半径 35px。タイミング σ=90ms でも接触率 100% | `battingSwingLingerDuration` 0.085 → 0.05 前後、または `batContactRadius` 35 → 28 | 三振率 10% 以上（目標 20〜30% は校正後に詰める）。README の「振り遅れの緩和」は残す |

**やり方**（1本ずつ、同じ手順）

1. ブランチを切る（`tune/<引き手名>`）。
2. 感度分析: 引き手を 0.6 / 0.8 / 1.0 / 1.2 倍で振って 9 カード × 12 試合を回す（`run-baseline.js --label tune-xxx`）。約 10 分。
3. 受け入れ基準を満たす値を候補にして、所見と同じ形式で before/after を `docs/balance/` に書く。
4. **人が実機で遊ぶ**（3回制を 2〜3 試合）。手応えが変わっていないか（特に「速く振れば強い」が残っているか）。
5. OK なら `physics` と README の「現在の主要パラメータ」を更新して main へ。
6. ハーネスの既存計測（`micro.js`）が同じ数字を出すことを確認する（走者側は触らないので変わらないはず）。

順番は **A → B → C**。A が守備の成立とHRの両方に効くので、A の結果を見てから B・C の必要量を決める。
A だけで 1 日、3本で 2〜3 日。

**やらないこと**: ボットの腕前が決めている数字（三振 0%、上級の勝率 100%）を目標に合わせ込むこと。校正前に追い込むと、校正後に戻すことになる。

## 3. テストプレイでデータを取る

### 3.1 設計方針

- **AI は見ていない。** 端末内の IndexedDB に記録するだけ。送信も通知もしない。
- **プレイヤーの手間は「書き出す」の1回。** 試合中は何もしない。
- **画面に情報を足さない**（方針2）。書き出しは既存の「リセット長押し」メニューに項目を1つ足すだけ。

### 3.2 実装（`app.js`）

- `testLog` と同じ形のイベントを本番でも `playLog` に積み、250ms デバウンスで IndexedDB に保存（既存の保存の仕組みに乗せる）。
- 記録する内容は `testLog` と同じ（投球・判定・打球・送球・アウト・得点・チェンジ）＋ **人の操作の生値**:
  - 投球: スワイプ速度・曲がり・リリース位置・狙いの通過 x
  - 打撃: スワイプ速度・振り始めの時刻と球の位置（タイミング誤差）・バット位置と球の x（横位置誤差）・芯度
  - 走者: 連打間隔の列、送球に対して止めたか
  - 守備: 拾えるようになってから拾うまでの時間、送球の先読み（狙い点と走者の実位置）
- 「リセット長押し」のメニューに `記録を書き出す` を足す。JSON をダウンロード（PC）または共有シート（iOS/Android の Web Share API）。
- 書き出した JSON は `docs/balance/playdata/<日付>-<端末>.json.gz` に置く（手で add して push。これが [4] のトリガー）。
- 個人情報は含めない（端末名も任意の文字列）。

### 3.3 必要な量

- 1 試合（3回制）で打席 20〜40、投球 40〜80。**腕前の分布を出すには 1 人あたり 5 試合、2〜3 人で十分**（打席 300 前後）。
- 1 セッション 30 分で足りる。

## 4. 評価（AI の使い分け）

### 4.1 作業と担当

| 作業 | 担当 | 理由 |
| --- | --- | --- |
| プレイ記録 → 人の精度分布（タイミング σ・横位置 σ・スワイプ速度・連打間隔・反応時間） | **スクリプト（AI なし）** `tools/balance/analyze-play.js` | 決まった集計。毎回同じ |
| 分布 → ボットの `PRESETS` 更新 | **Sonnet 5.5** | 分布を 3 段階に割る判断と、ボットのコード変更。ハーネスで妥当性を即確認できる |
| 更新したボットでベースライン再計測 | **スクリプト（AI なし）** `run-baseline.js` | 10 分で終わる。ローカルでも GitHub Actions でも |
| レポートの要約（10 行、目標帯からの外れを列挙） | **Haiku 4.5** | 定型。1 回あたり数千トークン |
| 「次に何を変えるか」の判断、仕組みの変更案、所見の執筆 | **Opus 5.5**（必要なら Fable 5.1） | ここだけが本当に判断が要る。1 反復に 1 セッション |
| コードの変更とハーネス検証 | **Sonnet 5.5**（引き手の数値変更）／ **Opus 5.5**（仕組みの変更） | 数値変更はハーネスが正解を出すので安い側で足りる |
| マージ前のレビュー | **人** | 実機で遊ぶのは人しかできない |

### 4.2 コスト感（API 単価: Haiku 4.5 $1/$5、Sonnet 5.5 $2/$10、Opus 5.5 $4/$20、Fable 5.1 $10/$50 ／ 入力/出力 100 万トークンあたり）

1 反復（データ取得 → 評価 → 改善 1 本 → 再計測）の目安:

| 項目 | トークン規模 | 概算 |
| --- | --- | --- |
| ハーネス実行・集計・分析スクリプト | 0 | ¥0（ローカル or Actions の無料枠） |
| Haiku の要約 ×2 回 | 入力 2 万・出力 2 千 | 数円 |
| Sonnet の校正・数値変更セッション | 入力 30〜50 万・出力 3 万 | ¥150〜250 |
| Opus の判断セッション 1 回 | 入力 30〜60 万・出力 3〜5 万 | ¥300〜500 |
| **合計** | | **¥500〜800 / 反復** |

Claude Code（定額プラン）で回す場合は API 課金ではなく利用枠の消費になるが、比率は同じ。**高い側（Opus/Fable）は判断の 1 セッションに絞り、見張り・定型・集計には使わない**のが要点。

### 4.3 「見張らない」ための仕組み

- **テストプレイ中: 何も動かない。** 記録は端末内。AI も Actions も走らない。
- **トリガーは push だけ。** `docs/balance/playdata/` に JSON が入った push で GitHub Actions が
  1. `analyze-play.js`（AI なし）で分布を出し `docs/balance/playdata/summary-<日付>.md` を生成
  2. `run-baseline.js` を現状のボットで回し、目標帯からの外れを `::warning::` で出す
  を実行する。ここまで AI 不使用。
- **要約が欲しいときだけ Haiku。** Actions の最後に Haiku で 10 行要約を PR コメント or `docs/balance/digest-<日付>.md` に書く（任意。無くても困らない）。
- **定期実行（Routine）は使わない。** 見るものがないときに起きても無駄。やるなら「週 1 の Haiku 要約」程度に留め、Opus の自動起動はしない。
- **Opus/Fable は人が呼ぶ。** 要約を見て「次を決めたい」と思ったときに、所見と最新レポートを渡して 1 セッション。

## 5. 改善の 1 反復（標準手順）

```
1. 人: テストプレイ（30 分）→ 記録を書き出す → docs/balance/playdata/ に push
2. Actions（AI なし）: 分布集計・ベースライン再計測・外れの警告
3. Haiku: 10 行要約（任意）
4. 人: 要約を見て、変える価値があるか判断。無ければここで終わり
5. Sonnet: 分布に合わせて PRESETS を校正 → 再計測（校正だけの反復もある）
6. Opus: 所見 + レポートを読んで「次に動かす引き手 / 変える仕組み」を 1〜3 案
7. Sonnet or Opus: 変更 → ハーネス → before/after レポート → PR
8. 人: 実機で遊んで採否 → マージ
```

1 反復 2〜4 日（人の時間が律速）。AI の実行時間は合計 1〜2 時間。

## 7. 決めてほしいこと

1. §1: PR 経由か直接マージか。
2. §2: A→B→C の順で進めてよいか。C（接触窓）は「振り遅れの緩和」の意図と衝突するので、A の結果を見てからでよいか。
3. §3: 書き出しの形式。ダウンロード（PC）＋共有シート（スマホ）の 2 経路でよいか。
4. §4: Haiku の要約を Actions に組み込むか（API キーを Actions のシークレットに置く必要がある）。無しなら完全に AI 不使用で、要約は人が呼んだときだけ。
